Формат файла flow (строгий парсер). Пиши flow молча; в твоём плане и работе ничего не меняется.

ЧТО:
- Есть письменный план работы (документ плана, план из plan mode, нумерованный план в чате): зеркаль его структуру как есть — по шагу на каждую задачу или раздел, которые он отслеживает, в том же порядке, коротким текстом, взятым из него на языке самого плана (сокращай, никогда не переводи), с его собственным номером/id в начале, если он есть («S4 2.1 Добавить миграцию»); больше ~6 пунктов → зеркаль только верхний уровень задач/фаз («S2 Phase 2: CLI»). `source:` = путь к документу плана (не указывай для плана только в чате). Никогда не правь документ плана ради flow; обновляй его так, как требует твой процесс.
- Письменного плана нет: flow — журнал сделанного, а не план. Никогда не перечисляй будущие шаги. Создай файл с только что законченным шагом как `[x] S1`; дальше каждый раз, закончив заметный шаг, добавляй его как `[x] S<n>` вместе с его строкой `step` одной правкой. Работай в том порядке, в каком работал бы и так.
- План ждёт одобрения пользователя: `status: review` до остановки. Одобрен → `active`. Попросили изменить → перепиши шаги под новый план и добавь строку `plan`.

---
title: <короткий заголовок, без #>
status: review | active | blocked | done
source: <путь к документу плана; только для зеркала>
---
## Goal
<одна строка>
## Steps
- [ ] S1 <текст>
## Journal
- plan #plan — <N шагов: кратко | «журнал сделанного»>

Шаги: один плоский список сразу под `## Steps` — без подзаголовков, вложенности и нумерованных пунктов. Маркеры [ ] не сделан, [x] сделан, [-] пропущен (почему), [!] блокер (почему); маркера «в работе» нет. Id S1, S2…; никогда не перенумеровывай и не переиспользуй. `→ <slug>` в конце = шаг передан субагенту; другими шагами стрелкой не заканчивай.
Журнал: только дописывать, новые внизу: `- <type>[/high] [S<n>] [#tag] — <текст>`; типы plan, step, deviation, decision, blocked, info; теги по желанию #scope #api #perf #test #refactor #risk #assumption #asset.

ОБНОВЛЯЙ только когда что-то завершилось или изменилось, ОДНИМ сообщением на событие (начало шага не отмечай). Не трать ход только на flow: отправляй его правки параллельно со следующим рабочим вызовом инструмента, а закрывающую правку — вместе с финальной проверкой (например, последним запуском тестов); если проверка не прошла, верни статус.
- шаг закончен: [x] + его строка `step` вместе
- работа расходится с зеркалируемым планом (шаг добавлен/убран/изменён, другой подход) → поправь шаги + строка `deviation` (`/high`, если меняется результат)
- `decision` — только когда ты сам выбрал между реальными вариантами во время работы и этого нет в плане; ответы и выбор пользователя — это `info`
- не можешь закончить шаг, потому что нужно что-то от пользователя (доступ, токен, решение) → [!] с причиной + строка `blocked` + `status: blocked` вместе, затем спроси в чате как обычно; такой шаг никогда не помечай [-]. [-] — только для шагов, убранных изменением плана или пользователем.
- всё решено → последний шаг [x] + его строка `step` + итоговая строка `info` + `status: done` вместе
Правь flow только через Write/Edit/MultiEdit, никогда через Bash. Текст на языке пользователя, кроме скопированного текста шагов.

SLUG: короткий kebab-case по задаче; добавь -2, если такой slug у flow другой задачи из списка. Один flow на задачу: доработки той же задачи остаются в её flow.
СУБАГЕНТЫ: переданные шаги веди в своём flow. Только если отдаёшь субагенту многошаговую часть работы, закончи его промпт строкой `[flow-handoff] slug=<child> parent=<твой-slug> step=S<n>` и закончи свой шаг на `→ <child>`.
